# BUG-008: Agent credential admission fails through the Access bypass

From: TC-207, TC-209, SPEC-014, SPEC-049, API-242, API-243. Found 2026-11-27 on the first-group deployment of commit `c309688` behind Cloudflare Tunnel and an Access Bypass application. At discovery the local-only workaround did not let agents on other hosts or the push job send snapshots; severity S2 is retained.

Reproduction reported by the deployment coordinator: issue a live agent credential, send the same credential to API-243 through the public endpoint, then to the server's loopback endpoint. The public request answered 401 `access_missing`, logged as `no_credential`; the loopback request answered 404 `project_not_found`, indicating that admission accepted the credential. Never record the credential, actual addresses or private paths in the evidence.

Expected: the public agent request reaches the server with the credential and API-243 returns its authenticated result. Actual: the public request was logged as `no_credential`; this does not by itself prove which headers reached the origin or whether both requests reached the same configured store. The point and reason for header removal are not yet independently isolated; Cloudflare documentation identifies those names as its own service-token headers but does not establish that Bypass strips them. A routing, proxy or client configuration difference remains possible.

Cause-stage hypothesis: the stage-06 API contract assumed the selected credential headers would reach the origin through the production gate. The point where the legacy headers were lost, if they were, was not isolated; the correction avoids relying on their forwarding.

Escape: local pinned-hub integration does not exercise a real Cloudflare Access Bypass path. Add an authenticated external push and a missing, wrong and revoked credential check to deployment QA, including the adjacent owner operations. The stage-12 gate had not been completed before the maintainer's first-group deployment instruction.

Correction and regression: NEXUS PR 170 corrected the API contract and server to accept a dedicated agent header pair while retaining the legacy pair; its BUG-008 regression failed before the correction and passed afterwards. The server correction merged as `0a6b152` and was deployed to the first-group server. Hub PR 228 merged as `e6b46ac` and the installed hub was updated on that server. On 2026-11-27 at 16:10 UTC the coordinator reported that the updated hub used an agent credential to push a real project through the Cloudflare edge: `getHeldCommit` and `pushSnapshot` each answered 200. This verifies the installed hub on the public route and TC-244; full issuance and revocation on the real server remain under TC-209. The repository push job still pins the older hub; its separate pin and credentials update and the full job check remain pending under TC-207. No address, credential or project identifier is recorded.
