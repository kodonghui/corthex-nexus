연결: TC-207, TC-209, TC-244, SPEC-014, SPEC-049, API-242, API-243. 2026-11-27 Cloudflare Tunnel과 Access Bypass 앱 뒤의 첫 그룹 배포 커밋 `c309688`에서 발견했다. 발견 당시 로컬 우회로는 다른 호스트의 에이전트와 push 작업이 스냅샷을 보낼 수 없었으며 심각도 S2를 유지한다.

배포 코디네이터가 보고한 재현: 유효한 에이전트 자격을 발급하고 같은 자격으로 공개 엔드포인트와 서버 루프백 엔드포인트의 API-243에 요청한다. 공개 요청은 401 `access_missing`, 로그 사유 `no_credential`이었고 루프백 요청은 404 `project_not_found`로 자격 검사를 통과했다. 자격, 실제 주소, 비공개 경로는 증거에 기록하지 않는다.

기대: 공개 에이전트 요청이 자격을 서버에 전달하고 API-243이 인증된 결과를 반환한다. 실제: 공개 요청은 `no_credential`로 기록되었다. 이 결과만으로 헤더의 원본 서버 도달 여부나 두 요청이 같은 설정의 저장소에 도달했는지는 확정할 수 없다. 어느 지점에서 어떤 이유로 헤더가 사라지는지는 독립적으로 확인하지 못했다. Cloudflare 문서는 해당 이름을 자체 서비스 토큰 헤더로 정의하지만 Bypass에서 제거한다고 명시하지 않으며 경로, 프록시 또는 클라이언트 설정 차이도 가능하다.

원인 단계 가설: 06단계 API 계약은 선택한 자격 헤더가 실제 게이트를 통과한다고 가정했다. 기존 헤더가 제거된 정확한 지점은 확인하지 못했으며 수정은 그 헤더의 전달에 의존하지 않는다.

누락 분석: 고정 hub의 로컬 통합 테스트는 실제 Cloudflare Access Bypass 경로를 거치지 않는다. 배포 QA에 외부 인증 push와 자격 누락·오류·폐기, 인접 소유자 작업 확인을 추가한다. 첫 그룹 배포는 관리자의 지시에 따라 12단계 게이트 완료 전에 진행됐다.

수정과 회귀 검증: NEXUS PR 170은 API 계약과 서버를 정정해 전용 에이전트 헤더 쌍과 기존 쌍을 각각 허용했다. BUG-008 회귀 테스트는 수정 전 실패하고 수정 후 통과했다. 서버 수정은 `0a6b152`로 병합해 첫 그룹 서버에 배포했다. hub PR 228은 `e6b46ac`로 병합했고 그 서버의 설치된 hub를 갱신했다. 2026-11-27 16:10 UTC에 코디네이터가 보고한 실제 프로젝트 push에서 갱신된 hub가 에이전트 자격으로 Cloudflare 엣지를 통과했으며 `getHeldCommit`과 `pushSnapshot`은 각각 200을 반환했다. 이 결과는 설치된 hub의 공개 경로와 TC-244를 검증한다. 실제 서버의 발급과 폐기 전체 검사는 TC-209에 남는다. 저장소의 push 작업은 아직 이전 hub에 고정되어 있으며 별도의 pin·자격 설정 갱신과 전체 작업 검사는 TC-207에 남는다. 주소, 자격 및 프로젝트 식별자는 기록하지 않는다.
