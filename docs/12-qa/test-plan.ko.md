# NEXUS v3: 테스트 계획

[English](test-plan.md)

12단계는 승인된 사용자 흐름(03), 기능 명세(04), API 계약(06), 화면 정의(08), 비기능 요구사항(02)을 테스트 케이스로 바꾸고, 케이스마다 실행 결과를 기록합니다. 이 첫 버전은 모든 케이스를 잇고, 상태는 모든 PR에서 이미 도는 테스트에서 가져옵니다(커밋 fd85323). 브라우저 점검, 아직 테스트로 고정되지 않은 고정 hub 실행, 실서버 케이스는 여기서 계획만 하고 실행하지 않았습니다. 브라우저 점검은 다음 PR에서 따로 합니다.

## 입력

- 사용자 흐름: `docs/03-user-flow/`, FL-001~FL-013, 화살표 156개.
- 기능 명세: `docs/04-functional-spec/spec.md`, SPEC-001~SPEC-052, 줄마다 인수 기준 하나(Must 43, Should 8, Could 1).
- API 계약: `api/openapi.yaml`, 오퍼레이션 52개, API-242~API-293, 응답 564개: 상태마다 그 상태가 적은 오류 코드 하나당 한 번씩 셈.
- 화면 정의: `docs/08-screens/`, SCR-142~SCR-146, 상태 39개.
- 비기능 요구사항: `docs/02-prd/requirements.md`, REQ-069~REQ-080 중 기능 요구사항인 REQ-079를 뺀 것: Must 6, Should 5.
- 11단계에서 넘겨받은 메모 25개. 각각 PR에서 승인된 답이나 WBS 4절이 여기로 보냄(3절).

### 1.3 응답을 받아 낸 것으로 세는 기준

오퍼레이션마다 API 테스트가 실제 서버의 응답을 모두 기록합니다. 그 확인인 `server/test/responses.js`의 `assertEvery`는 오퍼레이션이 적은 상태와 Problem 코드가 모두 돌아와 계약의 스키마에 맞을 때만 통과합니다. `default` 응답(500 `internal`)은 일부러 실패하게 만든 저장소에서 나옵니다: 일회용 저장소에 하는 통제된 결함 주입입니다. 목 서버에서 센 응답은 없습니다: 목에서만 확인한 응답 0개. 화면 테스트는 실제 서버의 응답을 페이지에 다시 돌려줍니다.

### 1.4 강제 실행

일일 백업과 30일 지난 백업 지우기(FL-011, SPEC-052)는 테스트에서 테스트 시계와 손으로 돌립니다. 로직은 확인되지만 실행 근거에 강제 실행으로 적고 게이트에는 실행하지 않은 것으로 셉니다. 강제하지 않은 확인은 하루 넘게 도는 실서버입니다(2.7절).

### 1.5 역할과 데이터

역할은 사용자(게이트로 로그인한 유일한 사용자), 에이전트(살아 있는 에이전트 자격을 가진 hub), 다른 사람(게이트로 로그인했지만 사용자가 아님), 로그인 없음입니다. 테스트는 일회용 저장소, 로그인, 자격을 스스로 만듭니다. 실제 자격이나 유료 서비스를 쓰는 케이스는 없습니다. NEXUS는 AI 모델을 부르지 않습니다(기능 명세 5절).

## 5. 커버리지와 릴리스 게이트

커밋 fd85323의 커버리지: 통과한 케이스가 흐름 13개 중 12개(전이 156개 중 150개), 인수 기준 52개 중 51개, API 응답 564개 중 564개, 화면 상태 39개 중 39개를 다룹니다. 목에서만 확인한 응답: 0개. 브라우저 점검은 커밋 fd85323에서 전이 156개 중 0개를 다뤘고 쓴 도구는 없습니다: 브라우저 점검은 따로 PR에서 합니다. 실행하지 않음: TC-037, TC-038, TC-097, TC-198~TC-202, TC-205~TC-213, TC-215~TC-221, TC-225~TC-243.

이 수는 커밋 fd85323 기준입니다. 게이트는 go/no-go 체크포인트 전에 릴리스 커밋에서 다시 적용합니다: 그때 막는 항목마다 pass가 있거나, 그 항목을 지목한 관리자의 면제 기록이 있어야 합니다. 배포한 v3가 있어야 하는 게이트 케이스(TC-037, TC-038, TC-097, TC-205~TC-212)는 배포 전에는 통과할 수 없고, 몇몇은 며칠이 걸립니다. go/no-go 체크포인트에서는 이것들을 첫 그룹에만 주는 go로 여쭙니다. TASK-464의 "먼저 12단계 릴리스 게이트를 통과함"은 게이트의 나머지 막는 항목이 통과하고 그 go를 받으면 채워집니다. v2를 끄는 넓은 릴리스는 이 케이스들이 하나하나 통과할 때까지 기다리고, 실패하거나 신호가 오지 않으면 멈추고 버그를 엽니다. 실행 L은 Windows에 POSIX 파일 권한이 없어 파일 권한 테스트 둘(백업의 것과 저장소의 것)을 건너뛰었고, 둘 다 실행 C(Linux)에서 통과했습니다. 실패한 케이스는 없습니다. 하나 열린 버그 BUG-001(S3)은 제품의 잘못이 아니라 테스트의 경쟁 조건이며 릴리스를 막지 않습니다.
