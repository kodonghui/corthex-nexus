# SCR-136 Checkpoint review

[한국어](SCR-136.ko.md)

Status: design definition; this does not claim implementation or a human review pass.

Purpose: The owning human reviews the exact published content and passes or withdraws its checkpoint.

## Actions

| Action | Result | Failure |
| --- | --- | --- |
| Request review (API-220) | Create a version-bound request with scope and review address. | Map refusal to error, permission or stale below; retain non-secret input. |
| Pass checkpoint (API-222) | Require the current owner session and expected revision/version; show one durable decision. | Map refusal to error, permission or stale below; retain non-secret input. |
| Withdraw checkpoint (API-223) | Confirm consequence and preserve the original pass and withdrawal history. | Map refusal to error, permission or stale below; retain non-secret input. |
| Navigate, theme, list selection | Use validated links, device theme and keyboard selection. | Return to the safe list if a target disappeared. |

## Layout and accessibility

At 320/390 use one column and a stage menu; at 768 collapsible navigation; at 1440 navigation/content/inspector. Wrap long titles and Korean without page overflow. Diagrams have a bounded scrolling canvas plus keyboard list; long source/code has its own region. Dialogs have names, focus containment, Escape and focus restoration. Announce status with aria-live and bind errors to fields. Main actions target 44px; every target at least 24px. Preserve all states in both themes.

Controls distinguish default, hover, pressed, focus, disabled, loading, selected and error. Prevent duplicate submission in flight, retaining its idempotency key for retry. An agent wait does not prevent a separate question. Clear private drafts/cache on account change/sign-out; never retain secret input after failure.
