# NEXUS v3: functional spec

[한국어](spec.ko.md)

Status: passed on 2026-11-23; the spec is frozen for the first release.

Inputs: the requirements ([requirements.md](../02-prd/requirements.md)) and the user flows ([README.md](../03-user-flow/README.md)), both passed on 2026-11-23, with the stage-01 glossary for names. One row per behaviour. Exceptions follow the kinds of cases: access, input, target, state changes, repeats, concurrency, limits, outside services, data exposure, empty answers and screen states.

## 1. Rules for every row

Each row adds only what differs from these rules.

1. Access. An owner action needs the owner's sign-in from the gate; a hub command needs a valid agent credential. A request with neither is refused and changes nothing (REQ-066). An agent credential on an owner-only action is refused as not allowed.
2. Target. An ID that is malformed, unknown or of a deleted item gets "not found" and changes nothing.
3. Repeats. Every write that the hub queues and every owner action that writes carries a request key; the same key again within 24 hours returns the first result and writes nothing. A push repeats by its commit, and a claim or a release by its session: the same commit answers its revision, and the same session's claim is the same claim.
4. Concurrency. Writes to one project run one at a time in arrival order; a write that the earlier one made invalid is refused with the reason.
5. Data exposure. No answer, page or log carries an agent credential's secret after it is issued, a credential digest, a sign-in token, a server path or the text of a refused file.
6. Outside services. NEXUS calls no AI model and never calls GitHub; agents bring what happens in Git. The only outside calls are reads of linked Notion and Jira status (SPEC-046).
7. Screen states. Every owner action ends in a result the owner can see: done, or refused with the reason in Korean and what to do next. Stage 08 decides how each looks.
8. Refused requests. Every refused request is logged with its time, the action, who sent it and the reason; the sender is the owner or a valid credential's name once checked, and "unknown" otherwise, never a name the request gives; the log follows rule 5. The sign-in gate keeps its own sign-in log and session expiry.

## 4. Choices this spec makes

No row adds a behaviour that no requirement asks for. These choices fill in exceptions within the requirements and are asked at the checkpoint:

- Limits the spec sets: a snapshot up to 8 MiB and a file up to 1 MiB (the pinned hub's file limit, kept by the hub), a comment up to 4,000 characters, a name up to 200 characters, a credential name up to 64, a Miro export up to 5 MiB.
- A request key on every write the hub queues and every owner write, and the same key within 24 hours returns the first result; a push repeats by its commit and a claim by its session.
- A confirmation is refused while change sets wait for reflection (SPEC-029), so a confirmation never covers a drawing Git does not hold.
- A reply to a closed thread is refused; a new comment starts a new thread (SPEC-017).
- A failed backup is retried once within the hour before the warning shows (SPEC-052), as decided at the stage-03 checkpoint.
- Revoking a credential also releases its claims (SPEC-050), so its work does not stay held.
- Cancelling a confirmation already recorded in Git asks the agent to record the cancel (SPEC-030).
- An AI proposal needs the claim on its comment (SPEC-018), so two sessions do not answer one comment.
- Accepting a proposal is refused when the document changed since it was made (SPEC-019), so the owner never accepts a change against an older version.
- A direct edit already in an open reflection pull request can still be cancelled, as REQ-028 says; the agent is asked to take it out of the pull request (SPEC-023).
- The record of a confirmation invalidated while it waited is accepted at its version and the confirmation stays invalidated (SPEC-032), so Git and NEXUS agree.
