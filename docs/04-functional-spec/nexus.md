## How to read this file

- Each row is one behaviour of NEXUS 0.2, which is phase ①, unless its status says that it comes later. `From` names the requirements and the flows it serves. Every functional Must requirement has at least one row; the non-functional requirements are listed under [The whole of NEXUS](#the-whole-of-nexus) and tested in QA (stage 12).
- Status says which release a row belongs to; stage 10 follows the building task by task. `built` for behaviour of phase 1 that 0.2 keeps as it runs, in `corthex-nexus` 0.1.0 and the server deployed on 2026-10-24; `active` for behaviour that 0.2 adds or changes; `later (phase ②)` for editing and workshops, first specified so that the data of 0.2 leaves room for them, and specified in full on 2026-11-07 from stage 01's frames for phase ②, to be built after the redesign; `planned` for behaviour that is specified and not yet in a release: the redesign's rows, SPEC-143 to SPEC-156, which are approved and built after NEXUS 0.2.3, and the rows of the design revision of 2026-11-11; `open (Dn)` was the status of a row of that revision that followed the recommendation of an open decision of stage 02, and no row says it since the maintainer decided D16 to D18 on 2026-11-12 as recommended. A release's task in stage 10 turns its rows to `active`. The tool links of phase ③ have no rows yet (REQ-186 to REQ-188).
- The design revision of 2026-11-11 added SPEC-187 to SPEC-210 and changed 20 rows that were passed before. In such a row, a sentence or a clause that begins with "from the design revision of 2026-11-11" is the revision's change: it is specified and not yet in a release, it passed the revision's checkpoint on 2026-11-12, and the rest of the row keeps the row's status. [For the checkpoint](#for-the-checkpoint) lists the changed rows.
- "The hub" is `hub.py` of the `corthex-hub` skill, on a device. "The server" is the NEXUS server, and "the view" the picture view in a browser. In the redesign's rows, "the first page" is the server's page at `/` (SCR-110) and "the workspace" a project's pages under `/p/` (SCR-111 to SCR-115), whose picture is the view. Stage 06 names their commands, requests and files. In the revision's rows, "the project's data" is the workspace's panel at `/p/{project}#data` (SCR-130).
- "The user" is a request that Cloudflare Access let in with a person's own sign-in, and "the agent" one that it let in with the service token (SPEC-116). For one person's projects, as now, the allowed people are the user. A repository's push job carries the service token too, and only pushes (SPEC-193).
- Numbers that a requirement gives, such as 1 MiB, 30 projects or 300 elements, are limits. The others, such as the lengths of comments, the 60 minutes of a claim and the 7 days of the outbox, are defaults of this release, which stage 06 fixes in the code and the trial may change. In the rows of phase ②, the 2 seconds of a save, the 10 seconds in which an open board shows changes, and the sizes and limits of drafts, notes, stickies, groups, frames and positions are defaults too. In the revision's rows, the 24 hours after which an entry that waits unread marks the last read, the 1,200 characters of a checkpoint request and the 50 notes of 200 characters that go with an edit are defaults; the ten lines of a request and the day after which the agent reads again come from the requirements.
- The stage skills are the skills of the core plugin, `corthex`, for each stage. Their new steps (REQ-086, REQ-131, REQ-154, REQ-167, REQ-168, REQ-181, REQ-212) and the core plugin's new `parts` setting are built with NEXUS 0.2; see [Notes for later stages](#notes-for-later-stages). The revision's steps (REQ-273, REQ-274, REQ-281, REQ-282, REQ-284, REQ-285, REQ-290) and the project settings' field that says that a project is expected on a NEXUS server are built with the release that holds the revision's rows.

## Answers to the points of the user flows

The [user flows](../03-user-flow/nexus/README.md#points-for-the-functional-spec) left eighteen points to this stage, and phase ②'s flows five more, 19 to 23, which the rows of phase ② answer. The design revision of 2026-11-11 left nine more, 24 to 32, which its rows answer, and it added to the answers to points 1, 13, 17 and 22.

| Point | Answer | Rows |

| 1. Where the drawing runs | Each step runs where it fits. The hub takes from the stage sources what each picture shows, its picture source, since it reads them anyway and has no time limit. The server stores each picture source as the picture of its document version, and cross-checks the pictures as it stores a snapshot, since discrepancies keep their state there; both are comparisons and writes, which fit the free plan's 10 ms of CPU time and 50 database queries for each request (Cloudflare's [Workers](https://developers.cloudflare.com/workers/platform/limits/) and [D1](https://developers.cloudflare.com/d1/platform/limits/) limits, read on 2026-11-02). The view lays the picture out and draws it, since a layout needs the sizes of the text, which only the browser measures. From the design revision of 2026-11-11: since the decision of 2026-11-04 the maintainer's server is the standalone runtime on the maintainer's existing VPS, where these two limits of the Workers Free plan do not apply and REQ-124 asks for under 1 second of processing for the largest push; the limits still bound the Worker build, which is kept as a compatibility path (see the decision of 2026-11-04 below). | SPEC-105, SPEC-118, SPEC-119, SPEC-120 |
| 2. Which checkout gives the pictures | Checkpoint choice 1, as recommended: only the default branch's commit. | 3. Which snapshot is newer | By ancestry, never by commit time: a child commit can carry its parent's time, and times can go backwards. Before a push the hub asks the server for the default branch commit that it holds, and sends the snapshot only when Git shows its own commit to be that commit or a descendant of it; the snapshot names the held commit as the one it replaces. The server stores a snapshot of another commit only while the commit it replaces is still the held one, and a snapshot of the held commit, or of a project for which it holds none, when it was made no earlier than the stored snapshot, as in phase 1. A device with an older fetch sends nothing, and the agent fetches and pushes again; of two pushes that replace the same commit, the second is refused and sent again. | SPEC-111, SPEC-112, SPEC-114 |
| 4. One project, several parts | Checkpoint choice 2, as recommended. The project settings name the parts, here `memory` and `nexus`. A document belongs to the part whose name starts its path in the stage source, such as `nexus.md`, `nexus/` or `memory-index.sql`. Each part has its own picture of each pictured stage and its own record of each stage. The records are in the repository as `.corthex/stages/<part>.json`, or `.corthex/stages.json` for a project without parts, in the format of phase 1's status file. | SPEC-105, SPEC-109, SPEC-118, SPEC-123, SPEC-137 |
| 5. The DDD board and the stage 01 template | The board needs nothing new from the template. The hub reads the template's forms: the contexts, their command-row tables with the policies among the rows, the external systems, the dependencies and the hotspots. It finds each aggregate's and read model's term by the glossary row of the same document whose term is its name; a TERM ID written beside the name, if the template comes to have one, wins. A name without its term is a check, not a discrepancy. So the open choice about the stage 01 template does not hold NEXUS up. | SPEC-106 |
| 6. Tables and screens with no term | A table or a screen names its terms by their TERM IDs, and one that stands for none says `terms: none`, such as a join table, a log or a sign-in screen. An aggregate or a read model that the part keeps without a table or a screen is listed in the ERD or the sitemap after `without a table:` or `without a screen:`. Only a table or screen that says neither opens a discrepancy for its missing term. | SPEC-107, SPEC-108, SPEC-120 |
| 7. What disagreeing means | Five kinds, each `warn` or `info`: a table or screen that names no term (`warn`); a table that names a term that no aggregate of the part's DDD board has, or a screen that names a term that no read model of it has (`warn`); an aggregate whose term no table names while the part has a current ERD, or a read model whose term no screen names while the part has a current sitemap, unless the ERD or the sitemap lists it after `without a table:` or `without a screen:` (`info`); a pair whose table or screen names another context than its aggregate or read model (`warn`); and a pair with one side marked removed (`warn`). An aggregate is compared only with tables, and a read model only with screens. A pair keeps one discrepancy with all its reasons, at the level of the most serious. | SPEC-121 |
| 8. A picture left out | The space keeps the last picture, marked as not current, with why: left out for size, or its source gone. A source in another repository is never drawn, and the view says so. A picture that is not current keeps its open comments and is cross-checked again only once it is current. A later snapshot that holds its source again makes it current: drawn anew if the source changed, or the same picture current again if not. | SPEC-105, SPEC-118, SPEC-119, SPEC-120 |
| 9. Answers and replies | A comment holds replies by the user and the agent. A user's reply can settle the comment, so that the agent records the decision, and a user's reply to a closed comment opens it again. | SPEC-127, SPEC-132 |
| 10. Proposals on the picture | The picture stays as its document version is. | 11. Reflections that do not go through | The agent reflects a pending reflection when its change still fits the latest stage source. When the items concerned changed or are gone, it asks the user on the comment, and the reflection waits, marked as needing the user. A pull request closed without being merged returns the reflection to pending, and the agent asks the user unless it opened another pull request for it. | SPEC-133 |
| 12. Two agents at once | The agent claims each entry of the agent to-do that it takes. A claim lasts 60 minutes from the session's last write on the entry, and the server refuses another session's writes on it meanwhile. | 13. The start of the agent's work | The entry skill and each stage skill read the agent to-do through the hub when they start, once in a session for the project; no hook is needed. A device without the service token says so and goes on. From the design revision of 2026-11-11: a session that cannot send says so once, only for a project that is expected on a NEXUS server, the agent reads again before each checkpoint request and once a day, and the server records each read (points 24, 25 and 27). | SPEC-135, SPEC-187, SPEC-190, SPEC-191 |
