# NEXUS: functional spec

[한국어](nexus.ko.md)

Stage 04 of CORTHEX's own project, for NEXUS: the `corthex-nexus` plugin and the NEXUS server. Status: draft of 2026-11-02, written while the memory plugin is being built, as the maintainer chose that day. The maintainer checks it together with the user flows of stage 03; after that check the rows are frozen for NEXUS 0.2, and a later change to a row needs the maintainer's decision. When this file and its Korean translation differ, this file is the source.

Inputs: the requirements in [docs/02-prd/nexus.md](../02-prd/nexus.md) (REQ-066 to REQ-193, REQ-197 and REQ-198), the user flows in [docs/03-user-flow/nexus/](../03-user-flow/nexus/README.md) (FL-101 to FL-115) and the glossary in [docs/01-domain/nexus.md](../01-domain/nexus.md), whose words this file keeps. This stage adds six words to the glossary (see [New words](#new-words)). The IDs of these rows start at SPEC-101, apart from memory's SPEC-001 to SPEC-039, so that both parts can add rows at the same time.

Two choices of the flows' checkpoint are still open: which version the pictures show, and how a project with several parts keeps its pictures and records. The rows follow the AI's recommendation for each, marked "checkpoint choice 1" and "checkpoint choice 2", and [For the checkpoint](#for-the-checkpoint) lists the rows that the other choices would change.

## How to read this file

- Each row is one behaviour of NEXUS 0.2, which is phase ①. `From` names the requirements and the flows it serves. Every functional Must requirement has at least one row; the non-functional requirements are listed under [The whole of NEXUS](#the-whole-of-nexus) and tested in QA (stage 12).
- Status: `built` for behaviour of phase 1 that 0.2 keeps as it runs, in `corthex-nexus` 0.1.0 and the server deployed on 2026-10-24; `active` for behaviour that 0.2 adds or changes; `later (phase ②)` for editing, specified now so that the data of 0.2 leaves room for it. The tool links of phase ③ have no rows yet (REQ-186 to REQ-188).
- "The hub" is `hub.py` of the `corthex-hub` skill, on a device. "The server" is the NEXUS server, and "the view" the picture view in a browser. Stage 06 names their commands, requests and files.
- "The user" is a request that Cloudflare Access let in with a person's own sign-in, and "the agent" one that it let in with the service token (SPEC-116). For one person's projects, as now, the allowed people are the user.
- Numbers that a requirement gives, such as 1 MiB, 30 projects or 300 elements, are limits. The others, such as the lengths of comments, the 60 minutes of a claim and the 7 days of the outbox, are defaults of this release, which stage 06 fixes in the code and the trial may change.
- The stage skills are the skills of the core plugin, `corthex`, for each stage. Their new steps (REQ-086, REQ-131, REQ-154, REQ-167, REQ-168, REQ-181) and the core plugin's new `parts` setting are built with NEXUS 0.2; see [Notes for later stages](#notes-for-later-stages).

## Answers to the points of the user flows

The [user flows](../03-user-flow/nexus/README.md#points-for-the-functional-spec) left eighteen points to this stage.

| Point | Answer | Rows |
| --- | --- | --- |
| 1. Where the drawing runs | Each step runs where it fits. The hub takes from the stage sources what each picture shows, its picture source, since it reads them anyway and has no time limit. The server stores each picture source as the picture of its document version, and cross-checks the pictures as it stores a snapshot, since discrepancies keep their state there; both are comparisons and writes, which fit the free plan's 10 ms of CPU time and 50 database queries for each request (Cloudflare's [Workers](https://developers.cloudflare.com/workers/platform/limits/) and [D1](https://developers.cloudflare.com/d1/platform/limits/) limits, read on 2026-11-02). The view lays the picture out and draws it, since a layout needs the sizes of the text, which only the browser measures. | SPEC-105, SPEC-118, SPEC-119, SPEC-120 |
| 2. Which checkout gives the pictures | Checkpoint choice 1, as recommended: only the default branch's commit. The hub reads the pictured documents and the stage records from the commit of the default branch that the checkout last fetched, through Git's object reader, so a work branch or uncommitted text never reaches a picture, whichever branch the checkout is on. | SPEC-105, SPEC-109 |
| 3. Which snapshot is newer | By ancestry, never by commit time: a child commit can carry its parent's time, and times can go backwards. Before a push the hub asks the server for the default branch commit that it holds, and sends the snapshot only when Git shows its own commit to be that commit or a descendant of it; the snapshot names the held commit as the one it replaces. The server stores a snapshot of another commit only while the commit it replaces is still the held one, and a snapshot of the held commit, or of a project for which it holds none, when it was made no earlier than the stored snapshot, as in phase 1. A device with an older fetch sends nothing, and the agent fetches and pushes again; of two pushes that replace the same commit, the second is refused and sent again. | SPEC-111, SPEC-112, SPEC-114 |
| 4. One project, several parts | Checkpoint choice 2, as recommended. The project settings name the parts, here `memory` and `nexus`. A document belongs to the part whose name starts its path in the stage source, such as `nexus.md`, `nexus/` or `memory-index.sql`. Each part has its own picture of each pictured stage and its own record of each stage. The records are in the repository as `.corthex/stages/<part>.json`, or `.corthex/stages.json` for a project without parts, in the format of phase 1's status file. | SPEC-105, SPEC-109, SPEC-118, SPEC-123, SPEC-137 |
| 5. The DDD board and the stage 01 template | The board needs nothing new from the template. The hub reads the template's forms: the contexts, their command-row tables with the policies among the rows, the external systems, the dependencies and the hotspots. It finds each aggregate's and read model's term by the glossary row of the same document whose term is its name; a TERM ID written beside the name, if the template comes to have one, wins. A name without its term is a check, not a discrepancy. So the open choice about the stage 01 template does not hold NEXUS up. | SPEC-106 |
| 6. Tables and screens with no term | A table or a screen names its terms by their TERM IDs, and one that stands for none says `terms: none`, such as a join table, a log or a sign-in screen. An aggregate or a read model that the part keeps without a table or a screen is listed in the ERD or the sitemap after `without a table:` or `without a screen:`. Only a table or screen that says neither opens a discrepancy for its missing term. | SPEC-107, SPEC-108, SPEC-120 |
| 7. What disagreeing means | Five kinds, each `warn` or `info`: a table or screen that names no term (`warn`); one that names a term that no aggregate or read model of the part's DDD board has (`warn`); an aggregate or read model whose term no table or screen names (`info`); a pair whose table or screen names another context than its aggregate or read model (`warn`); and a pair with one side marked removed (`warn`). A pair keeps one discrepancy with all its reasons, at the level of the most serious. | SPEC-121 |
| 8. A picture left out | The space keeps the last picture, marked as not current, with why: left out for size, or its source gone. A source in another repository is never drawn, and the view says so. A picture that is not current keeps its open comments and is cross-checked again only once it is current. A later snapshot that holds its source again makes it current: drawn anew if the source changed, or the same picture current again if not. | SPEC-105, SPEC-118, SPEC-119, SPEC-120 |
| 9. Answers and replies | A comment holds replies by the user and the agent. A user's reply can settle the comment, so that the agent records the decision, and a user's reply to a closed comment opens it again. | SPEC-127, SPEC-132 |
| 10. Proposals on the picture | The picture stays as its document version is. The view shows an accepted proposal over its items, marked as not yet reflected, until a redraw from the merged stage source holds the change. A dismissed proposal leaves its comment open, marked as having a dismissed proposal, so that the agent learns of it at its next work. | SPEC-130, SPEC-131 |
| 11. Reflections that do not go through | The agent reflects a pending reflection when its change still fits the latest stage source. When the items concerned changed or are gone, it asks the user on the comment, and the reflection waits, marked as needing the user. A pull request closed without being merged returns the reflection to pending, and the agent asks the user unless it opened another pull request for it. | SPEC-133 |
| 12. Two agents at once | The agent claims each entry of the agent to-do that it takes. A claim lasts 60 minutes from the session's last write on the entry, and the server refuses another session's writes on it meanwhile. An open pull request holds a reflection without a claim. | SPEC-136 |
| 13. The start of the agent's work | The entry skill and each stage skill read the agent to-do through the hub when they start, once in a session for the project; no hook is needed. The agent tells the user what is waiting. When the user asked for something else, it does that first and then the to-do; otherwise it works through the to-do in order. A device without the service token says so and goes on. | SPEC-135 |
| 14. Writes that fail | The hub keeps what it could not send in an outbox on the device and sends it at its next contact with the server; a write that the server refuses for good is reported and dropped. The view keeps a comment that could not be saved in the page and in the browser's storage until it is sent. Each write carries its own ID, so that sending it again leaves one result. | SPEC-126, SPEC-128, SPEC-129 |
| 15. A checkpoint before its record | The stage overview and the hub page show the stage's state as recorded, with the checkpoint passed in NEXUS beside it as waiting for its record, until a stage record names it. A withdrawal wins over a record that is not merged and pushed yet: the agent to-do lists the record's pull request for the agent to close, the agent checks before a merge that the checkpoint still stands, and a record merged anyway gets a `checkpoint-withdrawn` warning on its stage until the agent corrects it. | SPEC-123, SPEC-138, SPEC-139, SPEC-140 |
| 16. Telling the user from the agent | The server takes the kind of sign-in from the identity that Access checked: a service token's has the token's client ID and no user, and a person's sign-in has a user ([Access's application token](https://developers.cloudflare.com/cloudflare-one/identity/authorization-cookie/application-token/), read on 2026-11-02). Proposals, claims, decisions and reports of reflections and of record pull requests need the service token; accepting or dismissing a proposal and passing or withdrawing a checkpoint need a person's sign-in; comments and replies take either, marked with their author. | SPEC-116 |
| 17. Removal | The hub's dry run of a removal lists the space's open comments, open proposals, pending reflections and checkpoints not yet recorded, so that the agent can answer, reflect or record them first, and only then does the user confirm. | SPEC-115 |
| 18. The actions to ask about first | The snapshot holds the list with its source: the project's settings, the profile, or the core plugin's default list when neither sets one. A value that is not a list of strings counts as not set, with a check; an empty list means only what cannot be undone. The page shows up to 10 entries, the source, the profile's entries that the project's list leaves out, and that anything that cannot be undone is asked in any case. No level is shown, since the settings hold none. | SPEC-110, SPEC-125 |
