# NEXUS v3 서버

[English](README.md)

NEXUS v3의 서버예요. [WBS](../docs/10-wbs/wbs.ko.md)의 태스크 순서대로 만들어요. Node 24와 Node 자체 모듈로 돌아가고, 설치할 의존성이 없어요. v2처럼 Cloudflare Access 게이트 뒤에서 돌아가요.

TASK-413의 서버 골격, 곧 [api/openapi.yaml](../api/openapi.yaml)의 오퍼레이션을 위한 라우터, 환경 변수에서 읽는 설정, 요청마다 한 줄의 로그가 있어요. TASK-414의 저장소, 곧 [db/migrations](../db/migrations/)의 마이그레이션이 만드는 데이터베이스가 있어요. TASK-415의 요청 계층, 곧 오류 등록부, 본문 한도, JSON만 받기, 요청 키, 한 번에 하나씩 하는 쓰기가 있어요. TASK-416의 입장 확인, 곧 소유자 요청마다 게이트의 로그인이 한 소유자의 것인지 확인하는 부분이 있어요. 아직 받는 오퍼레이션이 없어서, 오퍼레이션을 만드는 태스크가 추가하기 전까지는 모든 경로가 `not_found` Problem으로 응답해요. 그리기 태스크가 쓰는 TASK-420, [그림 레이아웃](#그림-레이아웃)도 들어 있어요.

## 실행

```sh
cd server
NEXUS_DATA_DIR=/absolute/path/to/a/data/folder \
NEXUS_ACCESS_ISSUER=https://<team>.cloudflareaccess.com \
NEXUS_ACCESS_AUD=<the application's audience tag> \
NEXUS_OWNER_EMAIL=<the owner's email address> \
node src/main.js
```

꺾쇠 괄호 안의 값은 자리 표시자예요. 실제 값은 서버의 환경 변수에만 두고 Git에는 넣지 않아요.

## 설정

| 변수 | 기본값 | 뜻 |
| --- | --- | --- |
| `NEXUS_HOST` | `127.0.0.1` | 서버가 요청을 받는 주소예요. IP 주소나 `localhost`예요. 게이트의 터널은 같은 머신에서 서버에 접속해요. |
| `NEXUS_PORT` | `8787` | 포트, 0부터 65535까지예요. 0이면 시스템이 빈 포트를 고르고, 시작 줄이 그 포트를 알려요. |
| `NEXUS_DATA_DIR` | 없음 | 저장소를 두는 폴더의 절대 경로예요. 새 설치는 이 폴더를 소유자만 읽을 수 있게 만들어요. 저장소 파일은 폴더 권한과 상관없이 늘 소유자만 읽을 수 있어요. |
| `NEXUS_ACCESS_ISSUER` | 없음 | 게이트의 팀 주소 `https://<team>.cloudflareaccess.com`이에요. 게이트의 로그인 토큰이 발급자(issuer)로 적는 주소이고, 그 아래 `/cdn-cgi/access/certs`가 서명 키를 알려요. 경로, 포트, 쿼리가 없는 https origin이어야 해요. |
| `NEXUS_ACCESS_AUD` | 없음 | 게이트에 있는 NEXUS 애플리케이션의 audience 태그, 소문자 16진수 64자리예요. |
| `NEXUS_OWNER_EMAIL` | 없음 | 한 소유자의 이메일 주소예요. 게이트의 로그인에 담긴 대로 적고, 대소문자는 가리지 않고 비교해요. |

빈 변수는 기본값을 써요. `NEXUS_DATA_DIR`과 게이트 설정 세 개는 기본값이 없어서 꼭 설정해야 해요. 값이 올바르지 않으면 서버는 종료 코드 1로 멈추고, 설정 이름과 어긴 규칙을 적은 줄 하나만 남겨요. 잘못 넣은 값이 시크릿일 수 있어서 값은 적지 않아요.

## 저장소

저장소는 데이터 폴더 안의 SQLite 파일 하나, `nexus-v3.sqlite`이고, Node 자체 모듈 `node:sqlite`로 열어요(`src/store.js`). 서버는 요청을 받기 전에 저장소를 열고, 저장소에 아직 없는 `db/migrations`의 마이그레이션을 트랜잭션 하나로 적용해요. 그래서 마이그레이션이 실패하면 아무것도 바뀌지 않고 서버가 멈춰요. 아직 멈추는 중인 서버처럼 다른 연결이 잠금을 잡고 있으면 5초까지 기다려요. 새 설치는 빈 저장소로 시작해요(SPEC-015). 커밋 전에 멈춘 새 설치는 SQLite의 저널로 롤백되고, 다음 시작 때 다시 실행돼요.

- **스키마는 `db/nexus.sql`과 같아요.** 0001부터 빠짐없이 번호가 붙은 마이그레이션이 빈 데이터베이스에서 스키마를 만들어요. `test/store.test.js`는 마이그레이션이 만든 스키마와 `db/nexus.sql` 사이에 차이가 없는지 검사해요. 저장소는 자기 테이블을 따로 두지 않아요. 표시는 SQLite 헤더에 있어요. NEXUS v3의 application ID(`NXS3`)와, user version으로 적은 마지막 마이그레이션 번호예요.
- **다시 실행해도 아무것도 바뀌지 않아요.** 모든 마이그레이션이 적용된 저장소에는 쓰지 않아요.
- **v2 저장소는 읽지 않아요.** v2는 저장소 이름을 `nexus.sqlite`와 `rebuild.sqlite`로 썼고, v3는 `nexus-v3.sqlite`만 열어요. 그래서 같은 폴더에 있는 v2 저장소는 읽지 않은 채로 남아요. 저장소 이름을 가졌지만 NEXUS v3 저장소가 아닌 파일, 예를 들어 복사한 v2 저장소는 SQLite가 열기 전에 100바이트 헤더만 보고 거절하고, 그대로 둬요. 이 서버가 아는 것보다 새로운 서버가 더 마이그레이션한 저장소도 마찬가지예요.
- **마이그레이션.** 어디서든 한 번 적용된 마이그레이션은 고치지 않고, 다음 마이그레이션을 추가해요. `db/migrations`에 `.sql`로 끝나거나 숫자 네 자리로 시작하지만 `0001_initial.sql`처럼 이름 붙지 않은 파일이 있으면, 건너뛰지 않고 서버를 멈춰요. 서버는 저장소의 `db/migrations`를 읽으므로 저장소 체크아웃에서 실행해요. 마이그레이션이 테이블을 다시 만들 수 있도록 실행하는 동안에는 외래 키 검사를 끄고, 트랜잭션을 커밋하기 전에 모든 키를 검사해요.

핸들러는 `settings` 옆에서 열린 저장소를 `store`로 받아요.

## 입장 확인

요청은 입장 확인(`src/admission.js`)을 통과해야만 오퍼레이션의 핸들러에 닿아요. 그래서 거절한 요청은 저장소를 읽지 않고, 그 응답에는 프로젝트 데이터가 없어요. 무엇을 확인할지는 계약에 적힌 오퍼레이션의 `x-corthex` family가 정하고, `test/admission.test.js`가 서버의 목록을 계약과 비교해요.

- **소유자 오퍼레이션**은 게이트가 한 소유자에게 준 로그인만 들여요(SPEC-048, 규칙 1). Cloudflare Access는 이 로그인을 `Cf-Access-Jwt-Assertion` 헤더로 보내고, 쿠키나 다른 헤더는 읽지 않아요. `src/gate.js`가 Node 자체 모듈 `node:crypto`로 검증해요. 토큰의 `kid`로 발급자의 certs 엔드포인트가 알려 주는 키를 찾아 RS256 서명을 확인하고, 설정의 발급자와 audience, 만료 시각을 확인해요. 서버 시계보다 앞선 not-before 시각은 1분까지 봐줘요. 로그인이 없거나 만료됐거나 확인 하나라도 통과하지 못하면 `unauthenticated`(401), 소유자가 아닌 사람의 유효한 로그인이면 `not_owner`(403)예요.
- **소유자의 쓰기**(POST, PUT, PATCH, DELETE) 가운데 브라우저가 `Sec-Fetch-Site`로 NEXUS 자신(`same-origin`)이나 주소창(`none`)이 아닌 곳에서 왔다고 알리는 요청은 `cross_site`(403)예요. `Sec-Fetch-Site`가 없는 요청은 브라우저가 아니거나 이 헤더를 보내지 않는 오래된 브라우저에서 온 것이고, 들여요.
- **키**는 로그인을 처음 확인할 때 `<issuer>/cdn-cgi/access/certs`에서 읽어요. 5초 제한이 있고 리디렉션은 따르지 않으며, 한 시간 동안 써요. 서버가 모르는 `kid`가 오면 다시 묻지만, 10초에 한 번까지만 물어요. 2048비트 이상의 RSA 키만 써요. 현재 키를 읽을 수 없는 동안, 그리고 엔드포인트에 한 마지막 요청이 실패한 동안 서버가 모르는 `kid`가 오면 소유자 요청은 `internal`(500)이에요. 현재 키에 있는 `kid`는 그동안에도 확인해요. 이것이 서버의 유일한 바깥 호출이고, 서버 앞의 게이트에 하는 호출이에요. 테스트는 이것을 로컬 서명 키로 바꿔요.
- **에이전트 오퍼레이션**은 에이전트 자격 증명, 곧 `CF-Access-Client-Id`와 `-Secret` 쌍을 받고, TASK-417이 `src/admission.js`에서 확인해요. 그전까지는 모든 에이전트 요청이 `access_missing`(401)이고, 소유자 오퍼레이션에 온 에이전트 자격 증명은 소유자의 로그인이 없는 요청으로 다뤄요.
- **라우트**의 동작이 계약에 없는 것은 테스트만 만드는데, 확인 없이 들이려면 `family: 'none'`을 적어요. 계약에 없는 동작인데 그렇게 적지 않은 라우트는 서버를 만들 때 멈춰요. 그래서 family를 빠뜨려서 확인 없이 열리는 오퍼레이션은 없어요.

## 요청

라우트(`src/router.js`)는 오퍼레이션의 `operationId`를 `action`으로, 경로 파라미터마다 404 코드를 `params`로, 받는 본문의 종류를 `body`로, 요청 키를 받는지를 `requestKey`로 적어요. 요청은 다음 단계를 차례로 거치고, 어느 단계에서든 거절될 수 있어요.

1. **경로와 메서드.** 오퍼레이션이 없는 경로는 `not_found`로, 다른 메서드만 받는 경로는 `method_not_allowed`로 응답해요.
2. **입장 확인.** 요청은 경로 파라미터나 본문을 읽기 전에, 위에서 설명한 대로 오퍼레이션의 family에 따라 입장 확인을 거쳐요. 요청 키가 속하는 호출자는 입장 확인을 통과한 소유자 오퍼레이션이면 `owner`예요. 에이전트 오퍼레이션에는 TASK-417이 자격 증명의 ID를 줘요.
3. **경로 파라미터.** 경로 파라미터는 퍼센트 디코딩해요. 가리키는 대상에 대해 계약이 정한 형식이 아닌 값은 그 대상의 404를 받아요. 예를 들어 `{project}`는 `project_not_found`예요(`src/params.js`). 그래서 핸들러는 `/`, `..`, 제어 문자가 든 값을 받지 않아요. detail은 값을 되풀이하지 않아요.
4. **요청 키.** 요청 키를 받는 오퍼레이션은 계약 형식의 `Idempotency-Key`, 곧 큰따옴표 안의 write ID가 있어야 해요. 없으면 `field`가 `Idempotency-Key`인 `invalid_request`로 응답해요.
5. **본문.** 본문을 받는 오퍼레이션은 JSON 객체만 받아요(`src/body.js`).
   - `application/json`이 아니거나, charset이 UTF-8이 아니거나, 콘텐츠 인코딩이 있으면 `json_required`(415)예요.
   - 선언한 길이로 보거나 읽은 바이트가 넘어서는 순간 한도를 넘으면, 스냅숏(8 MiB)은 `snapshot_too_large`, Miro 내보내기(5 MiB)와 그 밖의 본문(2 MiB)은 `body_too_large`이고, `limit`이 함께 가요(413). 본문의 나머지는 읽지 않아요.
   - 객체의 UTF-8 JSON 텍스트가 아니면 `field`가 `body`인 `invalid_request`, 스냅숏이면 `invalid_snapshot`이에요(400).
6. **오퍼레이션.** 읽기는 바로 실행해요. 쓰기, 곧 메서드가 GET이 아닌 모든 오퍼레이션은 아래처럼 실행해요.

**읽지 않은 본문.** 거절처럼 본문을 끝까지 읽기 전에 보낸 응답은 본문의 나머지를 읽지 않은 채로 남겨요. Node는 연결이 다음 요청을 받기 전에 그런 본문을 끝까지 읽어요. 서버는 선언한 길이가 오퍼레이션의 본문 한도(본문을 받지 않는 경로는 2 MiB) 안일 때만 그렇게 하게 둬요. 그래야 아직 보내는 중인 호출자가 끊긴 연결이 아니라 응답을 읽어요. 더 긴 본문, 길이를 선언하지 않은 본문, 이미 일부를 읽은 본문은 연결을 닫아요(`Connection: close`). 그래서 서버는 받지 않은 본문을 그 한도보다 더 읽지 않아요.

**한 번에 하나씩 하는 쓰기**(규칙 4, `src/writes.js`). 쓰기는 요청이 위 단계를 통과하고 본문을 끝까지 읽었을 때 도착한 것으로 봐요. 서버 전체에 하나뿐인 큐에서 기다리다가, 프로젝트와 상관없이 앞선 쓰기가 끝나면 실행해요. 규칙 4는 한 프로젝트의 쓰기에 이것을 요구해요. 큐 하나는 그보다 엄격하고, 저장소가 허용하는 방식이기도 해요. 저장소는 SQLite 연결 하나이고, 연결 하나는 한 번에 트랜잭션 하나만 잡아요. 그래서 큰 스냅숏처럼 오래 걸리는 쓰기는 끝날 때까지 다른 프로젝트의 쓰기를 붙잡아요.

쓰기는 요청 키 확인부터 키의 행까지 트랜잭션 하나(`BEGIN IMMEDIATE`부터 `COMMIT`까지) 안에서 실행해요. 그래서 실패하거나 거절된 쓰기는 아무것도 바꾸지 않아요. 핸들러는 기다릴(`await`) 수 있고, 그동안 다음 쓰기도 함께 기다려요. 그사이 같은 연결에서 실행되는 읽기는 커밋 전의 행을 봐요. 그래서 쓰기 핸들러는 기다릴 일을 쓰기 전에 끝내요. 핸들러가 트랜잭션을 직접 시작하거나 끝내는 일은 없어요. 핸들러는 Problem을 던져서 거절해요. 성공 응답은 계약이 모든 성공에 정한 대로 200이나 201과 비어 있지 않은 JSON 객체예요. 다른 상태 코드, 그런 객체가 아닌 본문, 프레이밍 헤더처럼 그 밖의 응답은 결함이고 `internal`로 응답해요. 쓰기의 응답은 무엇이든 저장하기 전에 검사해요. 그래서 이런 쓰기는 아무것도 바꾸지 않아요.

**요청 키**(규칙 3, `src/keys.js`). 키마다 처음 응답을 TBL-169 `request_keys`에 보관해요. 이 테이블은 요청 계층의 테이블이에요. 키가 있는 모든 쓰기가 이 테이블을 채우므로 어느 오퍼레이션도 이 테이블을 적지 않아요(WBS 메모 21).
- 같은 호출자가 7일 안에 같은 키를 보내면 처음 상태 코드와 응답을 받고, 아무것도 쓰지 않아요. 키는 응답의 상태 코드와 본문을 보관하고, 쓰기 자체의 헤더는 보관하지 않아요. 계약에서 요청 키를 받는 오퍼레이션에는 그런 헤더가 없어요. 규칙 3이 요구하는 24시간보다 긴 7일 동안 키를 보관해요. hub가 보내지 못한 쓰기를 그만큼 보관했다가 같은 키로 다시 보내기 때문이에요.
- `action` 열에는 `operationId`, 공백, 요청의 경로와 본문 바이트의 SHA-256(16진수)을 적어요. 그래서 다른 오퍼레이션, 다른 경로, 다른 본문으로 같은 키를 다시 보내면 다른 action이 되어 `request_key_reused`(409)를 받아요. 이 다이제스트는 요청의 다이제스트이고 자격 증명의 다이제스트가 아니에요. 소유자만 읽는 저장소에만 있고, 어떤 로그 줄에도 들어가지 않아요(규칙 5).
- 거절되거나 실패한 쓰기는 키를 남기지 않아요. 그래서 같은 키로 다시 실행돼요.
- 키는 호출자(`actor`: `owner`나 자격 증명의 ID)의 것이어서, 두 호출자의 키는 서로 만나지 않아요.
- 새 키를 쓸 때 7일보다 오래된 키를 모두 지워요.
- 라우트의 `repeat(result)`는 처음 응답 대신 반복 요청이 받을 응답을 정해요. API-280은 이것으로 시크릿을 보관하지 않고, 반복 요청에 200과 `secret` null로 응답해요.

## 응답

- 오퍼레이션은 JSON으로 응답해요. 거절은 `application/problem+json`의 Problem이고, `title`, `status`, `detail`, `code`, `traceId`와, `field`나 `limit`처럼 그 코드가 가진 멤버가 있어요. 형식은 계약의 `components.schemas.Problem`과 정확히 같아요.
- 등록부(`src/problem.js`)는 `components.x-corthex.errors`의 모든 코드를 상태 코드, 제목, 멤버, `message`, `message_ko`와 함께 보관해요. Problem 스키마는 다른 멤버를 허용하지 않으므로 두 메시지는 응답에 넣지 않아요. 두 메시지는 등록부에 `ERRORS`로, 그리고 각 `Problem`에 남아서, 화면이 코드로 거절 이유와 다음에 할 일을 한국어로 보여 줄 수 있어요(규칙 7). 앱 셸인 TASK-454가 이것을 화면에 제공해요.
- 오퍼레이션이 없는 경로는 `not_found`(404)로 응답해요. `/api/spaces` 아래에서는 detail이 NEXUS가 받는 에이전트 명령 push, todo, claim, comment, decide, reflect, status, record를 알려요(SPEC-014). detail은 요청의 경로를 되풀이하지 않아요.
- 다른 메서드만 받는 경로는 `Allow`와 함께 `method_not_allowed`(405)로 응답해요.
- 입장 확인이 거절한 요청은 위에 적은 대로 `unauthenticated`(401), `not_owner`(403), `cross_site`(403), `access_missing`(401) 중 하나로 응답해요.
- 핸들러가 실패하면 `internal`(500)로 응답하고, 그 `traceId`로 로그에서 요청을 찾아요.

## 로그

서버는 요청마다 응답이 끝나거나 연결이 끊길 때 표준 출력에 JSON 한 줄을 써요.

| 필드 | 값 |
| --- | --- |
| `time` | 요청이 들어온 시각, UTC예요. |
| `traceId` | 임의의 16진수 16자리예요. 소유자의 로그인을 들였고 게이트의 `CF-Ray`가 계약의 `traceId` 형식(16진수 16자리, 하이픈, 데이터 센터의 영문 3자)이면 그 값을 써요. 게이트를 거치지 않고 서버에 닿는 누구나 `CF-Ray`를 보낼 수 있지만, 소유자의 로그인에는 게이트만 서명해요. 다만 로그인은 bearer 토큰이라서, 그 토큰을 가진 사람이 게이트를 거치지 않고 loopback의 서버에 닿으면 자기 요청의 ray는 고를 수 있어요. Problem 응답에도 같은 ID가 들어가요. |
| `method` | 요청의 메서드예요. |
| `action` | 오퍼레이션의 `operationId`예요. 오퍼레이션이 없는 경로는 `null`이에요. |
| `sender` | 요청을 보낸 이예요. 소유자의 로그인을 들이면 `owner`, 아니면 `unknown`이고, 요청이 스스로 대는 이름은 적지 않아요(규칙 8). |
| `status` | 응답의 상태 코드예요. 응답을 시작하기 전에 연결이 끊기면 `null`이에요. |
| `code` | Problem의 코드, 없으면 `null`이에요. |
| `ms` | 응답에 걸린 시간, 밀리초예요. |
| `reason` | 유효한 로그인이 없어서 소유자를 들이지 않았을 때만 있어요. 통과하지 못한 확인으로 `no_sign_in`, `malformed`, `unknown_key`, `bad_signature`, `wrong_issuer`, `wrong_audience`, `expired`, `not_yet_valid` 중 하나이고, 키를 읽지 못했으면 `keys_unavailable`이에요. |
| `error` | 핸들러가 실패했거나 거절 응답을 보내지 못했을 때만 있어요. 오류 종류로, 내장 오류 타입과 Node의 코드가 있으면 그 코드예요. 예: `Error ENOENT`. |
| `aborted` | 응답이 끝나기 전에 연결이 끊겼을 때만 있어요. 값은 `true`예요. |

요청을 받기 시작할 때(호스트와 포트 포함), 멈출 때, 설정이 올바르지 않을 때도 한 줄을 쓰고, 크래시가 나면 Node의 보고 대신 한 줄을 써요. 요청을 받기 전에는 저장소에 관한 줄을 하나 써요. 저장소의 `version`과 적용한 마이그레이션 `applied`를 담은 `store_opened`, 이유 `reason`(`not_a_v3_store`, `newer_store`, `migrations_invalid`, `foreign_keys_broken` 중 하나)을 담은 `store_refused`, 오류 종류 `error`를 담은 `store_failed` 중 하나예요. 어느 줄도 데이터 폴더를 적지 않아요.

그래서 거절한 요청은 모두 시각, 동작, 보낸 이, 까닭(Problem의 `code`)과 함께 로그에 남아요(규칙 8).

[기능 명세](../docs/04-functional-spec/spec.ko.md)의 규칙 5에 따라 에이전트 자격 증명의 시크릿, 자격 증명 다이제스트, 로그인 토큰, 서버 경로, 거절한 파일의 텍스트는 어떤 로그 줄에도 들어가지 않아요. 그래서 어떤 필드도 요청(경로, 쿼리, 헤더, 본문)이나 오류의 메시지·스택에서 복사하지 않아요. `test/logs.test.js`, `test/main.test.js`, `test/admission.test.js`가 데이터 폴더, 소유자의 로그인, 이메일까지 포함해, 실행할 때 만든 값으로 이것을 검사해요. 게이트 설정과 요청 키의 다이제스트도 어떤 줄에도 적지 않아요. 다이제스트는 `test/keys.test.js`가 검사해요.

## 그림 레이아웃

`src/layout.js`는 TASK-420이에요. DDD 보드, ERD, 사용자 흐름, 사이트맵 트리(SPEC-003, SPEC-004, SPEC-006, SPEC-007)의 박스와 선을 놓는, 위에서 아래로 가는 계층형 레이아웃이에요. 그리기 태스크인 TASK-421부터 TASK-425가 박스와 선을 넘기고, 돌려받은 결과를 그려요. 레이아웃 자체는 아무것도 그리지 않아요. [WBS](../docs/10-wbs/wbs.ko.md)의 질문 3에서 ELK나 dagre 같은 레이아웃 라이브러리를 쓰지 않고 이 저장소에서 직접 만들기로 정했어요. 아무것도 import하지 않아서 페이지도 같은 파일을 불러올 수 있어요.

```js
import { layout } from './layout.js';

const { bounds, nodes, edges } = layout({
  nodes: [
    { id: 'TBL-146', width: 200, height: 120 },
    { id: 'TBL-167', width: 200, height: 80 },
  ],
  edges: [{ from: 'TBL-167', to: 'TBL-146', label: { width: 40, height: 16 } }],
});
```

| 입력 | 뜻 |
| --- | --- |
| `nodes[].id` | 박스의 키예요. 다른 박스와 겹치지 않는 텍스트로, 요소의 키 같은 값이에요. |
| `nodes[].width`, `nodes[].height` | 박스의 크기, 1부터 100000까지예요. |
| `nodes[].layer` | 선택 사항이에요. 박스를 0부터 1000까지의 계층에 고정해요. 예를 들어 보드에서 스티키 노트 종류별 행이에요. 없으면 그 박스를 가리키는 모든 박스보다 한 계층 아래에 놓여요. |
| `nodes[].position` | 선택 사항이에요. 소유자가 박스를 놓은 `{ x, y }`예요(SPEC-012). 박스는 그 자리에 있고, 다른 박스는 그 박스를 피해요. TASK-442가 채우고, 이 태스크는 이동 기능을 만들지 않아요. |
| `edges[].from`, `edges[].to` | 선이 잇는 두 박스의 id예요. |
| `edges[].label` | 선택 사항이에요. 선의 레이블에 필요한 공간 `{ width, height }`예요. |
| `direction` | 옵션이에요. `TB`는 계층을 위에서 아래로(기본값), `LR`은 Mermaid `flowchart LR`처럼 왼쪽에서 오른쪽으로 놓아요. |
| `nodeGap`, `layerGap`, `edgeGap` | 옵션이에요. 한 행에서 두 박스 사이 간격(32), 두 행 사이의 최소 간격(48), 나란히 가는 두 선 사이와 선에서 레이블까지의 간격(12)이에요. |

`nodes`와 `edges`를 입력 순서대로 돌려줘요. 노드에는 `id`, `x`와 `y`(왼쪽 위 모서리), `width`, `height`, 받은 계층 `layer`, 위치를 지켰는지 나타내는 `fixed`가 있어요. 에지에는 `from`, `to`, 첫 박스의 가장자리에서 두 번째 박스의 가장자리까지의 `points`, 레이블 박스 `label` 또는 `null`이 있어요. `bounds`는 전부를 담는 박스로 SVG `viewBox`에 써요. 그 모서리가 0에 있지 않을 수 있어요.

- 같은 입력은 같은 출력을 내요. 동점은 모두 입력 순서로 정하고, 시계나 난수에 기대지 않으며, 숫자는 소수점 둘째 자리까지 반올림해요.
- 레이블을 포함해 두 박스가 겹치지 않아요. 레이아웃이 놓는 박스는 고정된 박스도 피해요. 고정된 두 박스는 소유자가 놓은 것이라 겹칠 수 있어요.
- 선은 박스의 아래에서 나가 다음 박스의 위로 들어가요(`LR`에서는 오른쪽과 왼쪽). 가로와 세로로만 가고, 두 행 사이 간격에서 자기 트랙을 따라 꺾여서 박스나 레이블을 지나지 않아요. 레이블은 선 옆에 놓여요. 자기 박스로 가는 선이나 한 계층에 고정된 두 박스 사이의 선은 그 행 아래로 내려갔다 돌아와요. 흐름에서 앞 단계로 되돌아가는 선처럼 사이클을 닫는 선은 위를 가리켜요. 결정의 마름모처럼 직사각형이 아닌 모양을 그리는 그리기 태스크는 첫 점과 마지막 점을 그 선분을 따라 모양의 윤곽까지 옮겨요.
- 고정된 박스로 가는 선은 박스 가장자리에서 선의 다음 점까지 곧게 가고, 다른 박스를 지날 수 있어요.
- 어떤 선으로도 이어지지 않은 박스들은 입력 순서대로 나란히 서고 행을 함께 써요. 예를 들어 보드의 열이 시간 순서대로 서요.
- 올바르지 않은 입력은 필드와 그 규칙을 알리는 `TypeError`나 `RangeError`를 던지고, 값은 적지 않아요.
- 박스와 선이 행을 지나는 점을 합해 200000개보다 많이 필요한 그래프는 `RangeError`로 거절해요. 어떤 입력도 호출한 쪽을 오래 붙잡지 않게 하려는 거예요. 테스트에서 가장 빽빽한 300개 요소 그래프는 약 23500개가 필요해요.
- `test/layout.test.js`는 각 모양에서 300개 요소를 검사 러너에서 1초 안에 놓아요. REQ-070의 2초의 절반이고, 2초는 12단계에서 브라우저로 측정해요.
